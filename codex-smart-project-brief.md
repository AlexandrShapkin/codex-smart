# Codex Smart — project brief and engineering backlog

**Версия документа:** 2026-10-06 · **Исходный baseline:** `codex-toolkit v1.4.1` (архив от 2026-09-23)

## 1. Миссия

Создать автономную надстройку над Codex CLI для задач разработки. Максимизировать правильность, полноту, поддерживаемость и проверяемость изменений при минимальном **необходимом** расходе токенов и приемлемых задержках.

**Правило приоритета:** соблюдение требований, безопасность и необходимая проверка — ограничения; внутри этих ограничений минимизировать затраты. Не экономить за счёт пропуска существенного контекста, тестов, регрессий и impact analysis.

## 2. Подтверждённый baseline

По исходникам архива `v1.4.1`:

- `scripts/codex-smart` запускает `codex --profile`; профиль по умолчанию **всегда `lean`**. `graph`, `semantic`, `deep` выбираются вручную через `--toolkit-profile` или переменную окружения.
- `scripts/classify_repo.py` определяет корень, языки, размер и приблизительное число строк, но результат маршрутизатору не нужен (показывается в `--explain`).
- `skills/tool-router/SKILL.md`: native-first; CodeGraph CLI — по необходимости для архитектуры/impact; Serena — ручной/специализированный fallback; Context7 — внешняя документация.
- `code-graph-smart` вызывает локальный `code-graph-mcp` или `npx -y -p @sdsrs/code-graph code-graph-mcp`.
- `lean` отключает MCP Serena и CodeGraph. `semantic` включает Serena, `graph` и `deep` включают CodeGraph; `deep` использует High reasoning, остальные — Medium.
- `bootstrap.sh` устанавливает скрипты, профили и skills, изменяет пользовательский `~/.codex/config.toml` через `scripts/patch_config.py`; в `v1.4.1` удалены устаревшие manual MCP overrides для `serena_repl` и `context7`.
- Имеется воспроизводимый benchmark harness v4 для анализа путей выполнения в чужих кодовых базах. Это **не** benchmark качества реализации изменений.
- Установленная локально на ThinkPad версия на 2026-10-06 не проверена; сверка checksum и конфигурации обязательна до миграции.

### Результат имеющегося benchmark

24/24 прогона прошли evidence/backend gates на 6 репозиториях (ripgrep, just, Caddy, Task, HTTPX, Ansible), 4 режима (native/graph/Serena/hybrid).

| Режим | Median fresh input | Median total input | Median wall time |
|---|---:|---:|---:|
| Native | 62 588 | 354 167 | 74,0 с |
| Graph | 57 390 | 323 090 | 76,2 с |
| Serena | 71 929 | 531 049 | 100,0 с |
| Hybrid | 59 985 | 438 353 | 120,7 с |

CodeGraph уменьшил медианный fresh input на 8,3% относительно native, однако выиграл по этому показателю только в 3/6 репозиториев. Вывод: не выбирать backend только по языку/размеру репозитория; не делать все MCP постоянно активными.

## 3. Подтверждённые недостатки и обязательные исправления

### P0 — корректность, безопасность, воспроизводимость

1. **Не скрывать необходимые инструменты из-за выбора `lean`.** Сделать разведку возможностей до старта задачи: native, CodeGraph CLI/MCP, Serena MCP, Context7, GitHub, инструменты языка. Для анализа архитектуры и сложного рефакторинга подобрать подходящий *tool surface* до начала сессии; в сессии агент самостоятельно выбирает метод. Если сервер отсутствует, использовать проверенный CLI/fallback. Никаких заявлений о доступности без реального `preflight`.
2. **Убрать побочные изменения из `codex-smart` / `--explain`.** Сейчас обёртка без запроса добавляет `.code-graph/` и `.serena/` в `.git/info/exclude`, включая режим `--explain`. Требуется чтение без мутаций, отдельная политика локальных кэшей/артефактов, запрет скрывать проектные Serena memories без решения владельца.
3. **Безопасная конфигурация.** `bootstrap.sh`/`patch_config.py` должны быть транзакционными и идемпотентными, не сбрасывать пользовательские MCP/профили/плагины, не отключать ранее включённые инструменты вне явной политики, иметь dry-run, diff, backup, rollback. Сохранить ChatGPT keyring auth и Context7 plugin.
4. **Воспроизводимые внешние инструменты.** Закрепить версии CodeGraph и прочих зависимостей; не допускать скрытых `npx -y` скачиваний на каждом запуске; отдельная установка только с согласия. Проверять поддерживаемые команды CLI и схемы MCP по текущим версиям.
5. **Compatibility tests.** Проверять `hooks = true` вместо legacy `codex_hooks`, актуальный `serena-hooks` (`reset` отсутствует в проверенной Serena 1.7.0), транспорт/названия инструментов MCP, работу `--profile`, не дублировать Context7 plugin как manual MCP.
6. **Убрать недоказанные эвристики.** `classify_repo.py` не должен тратить ресурсы на сканирование файлов, если данные не участвуют в решении. Характеристики, если нужны, должны быть дешёвыми, кэшируемыми и валидируемыми.

### P1 — функциональная маршрутизация и автономность

7. **Маршрутизация по задаче, а не только размеру репозитория:** точечная правка, диагностика, архитектура, impact, рефакторинг, тесты, зависимые внешние API, GitHub/CI. Поддержать явное предпочтение пользователя и сложность/риск.
8. **Двухуровневая маршрутизация:** до запуска определить необходимую доступность (профиль/capability set), внутри Codex выбирать вызовы инструментов по ожидаемой информативности/стоимости. Не предполагать динамическое подключение MCP во время активной сессии без подтверждённой поддержки. Для текущих BG1/RF1/VS1 включать средства архитектурного анализа при необходимости и выбирать Medium/High reasoning по риску задачи.
9. **Целевая политика эскалации:** native для точного и локального; CodeGraph для графа архитектуры/трассировки/impact; Serena для точных семантических ссылок/символов/рефакторинга; Context7 для внешних версионных API; GitHub для удалённых Issues/PR/CI; native build/test/lint для проверки. При нехватке доказательств эскалировать, а не угадывать. Не повторять эквивалентные исследования.
10. **Контекст по ступеням:** сначала архитектурная карта/символы, затем точные тела и участки, только затем более широкие файлы. Ограничивать размер ответов инструментов, фильтровать шум, сохранять ссылки на исходники, не подменять проверку реального кода графовой аннотацией.
11. **Reasoning effort на уровне задачи:** Medium по умолчанию, High при сложной архитектуре, неопределённости, риске и многочисленных зависимостях. Не повышать reasoning только из-за общего объёма репозитория. Учесть расходы/время и не ухудшать корректность.
12. **Системная инструкция:** закрепить выбор любого доступного инструмента по полезности, стоимости и достоверности в `AGENTS.md`, `docs/TOOLING.md` и `docs/WORKFLOW.md`. Синхронизировать с `tool-router` skill. Избегать дублирующего длинного текста в каждом файле.

### P2 — измеримость и качество

13. **Новый benchmark разработки**, а не только чтения: задачи исправления багов, точечного редактирования, рефакторинга с несколькими модулями, новых функций, тестов, анализа больших репозиториев, работы с Go/Rust/Python и IaC. Заранее фиксировать независимые правильные тесты/диффы и критерии качества.
14. **Телеметрия:** usage.input_tokens, cached_input_tokens, fresh_input_tokens, output_tokens (включая reasoning, если доступно), время, число и успехи вызовов, повторы/перезапуски, стоимость и стабильность. Отдельно измерять cold/warm index и подготовку инструментов. Сохранять агрегаты, а не содержимое секретов/промптов из приватных репозиториев.
15. **Сопоставимость:** один и тот же snapshot, модель, параметры, изолированная среда, одинаковое ТЗ, порядок вариантов рандомизирован, несколько повторов на сценарий, учёт неудач и bootstrap/index overhead.
16. **Quality gates:** независимые unit/integration tests, сборка, линтер/типизация при наличии, регрессионный и security-check, проверка охвата требований, reviewer assessment для архитектурных задач. Evidence-validity сама по себе не равна качеству разработанного кода.
17. **Оптимизация по Pareto frontier:** сначала отсеивать варианты, ухудшающие корректность или безопасность; среди сопоставимых по качеству выбирать меньшие fresh/total tokens и задержку. Дорогой анализ оправдан, когда он реально снижает риск неверного изменения, повторной работы или регрессии.

### P3 — продуктовая завершённость

18. Диагностический `codex-smart doctor`: installed/runtime health, доступность каждого capability, статус индекса, версии, предупреждения о несовместимости, ссылки на исправления без раскрытия токенов.
19. `codex-smart --explain` показывает выбор tool surface, причину, эффект для стоимости, альтернативы и уровень уверенности, ничего не изменяя.
20. CI: unit для маршрутизатора/классификатора/конфиг-патчера, интеграционные smoke-тесты с stub MCP и CLI, матрица Codex/Serena/CodeGraph совместимости.
21. Независимый репозиторий: версионирование, changelog, миграция из `codex-toolkit`, упаковка без `__pycache__`, лицензия, документация, rollback.

## 4. Предлагаемая архитектура

```text
User task / project specification
              │
              ▼
codex-smart (thin, deterministic launcher)
  ├── task hints, risk, repo facts (cached)
  ├── capability preflight (cheap, offline by default)
  ├── select tool surface + reasoning
  └── emit auditable reason + fallback plan
              │
              ▼
Codex CLI (one coherent agent session)
  ├── native shell/git/tests (default)
  ├── CodeGraph CLI on demand
  ├── Serena MCP for semantic operations (when enabled)
  ├── CodeGraph MCP selectively (only if measured benefit)
  ├── Context7 plugin for external docs
  └── GitHub CLI/plugin when remote operations needed
              │
              ▼
Verifiable changes + tests/CI + token/latency metrics
```

**Без обязательного собственного MCP-сервера, векторной БД или локальной LLM.** Обёртка не должна дублировать возможности самого Codex.

## 5. Не-цели на первом этапе

- Глобальное включение всех MCP для каждого запроса.
- «Обязательное использование» каждого подключённого инструмента.
- Генерация архитектурных графов ради графов.
- Добавление `saiprashanths/code-analysis-mcp` — он дублирует дерево/чтение файлов и не предоставляет полноценный static analysis.
- Принудительное сведение всех задач к `lean` либо всех сложных задач к `deep`.
- Скрытое обновление окружения, автоматический push/deploy/merge.

## 6. Порядок работ

1. **Baseline import/audit.** Поместить `v1.4.1` в новый репозиторий, проверить архив, локально установленную версию, конфигурации/хук/ключи, сохранить результаты старого benchmark и требуемую совместимость.
2. **Correctness and safety fixes (P0).** Сделать `--explain` чистым, исправить bootstrap/patcher, pin версий, preflight возможностей; добавить автоматические тесты.
3. **Router v2 (P1).** Задача → capability set → рабочий профиль; модель сама выбирает инструмент в разрешённом наборе; сделать fallback/escalation явным.
4. **Development benchmark (P2).** Сравнить с vanilla/native, текущей v1.4.1 и улучшенными режимами на одинаковых задачах.
5. **Production hardening (P3).** CI, `doctor`, упаковка, migration/rollback, версия 2.0 только после quality gates.

## 7. Минимальные acceptance criteria

- На том же наборе задач качество не ниже проверяемого baseline; все обязательные проектные тесты проходят.
- Система не скрывает Serena/CodeGraph, когда они требуются выбранному сценарию и доступны на машине; недоступность корректно отражается в diagnostics.
- Простые задачи не оплачивают постоянный overhead тяжёлых MCP без оправдания.
- Реальный выбор инструментов/эскалация фиксируются; нельзя выдавать вызов `rg` за графовый/семантический анализ.
- `--explain` и `doctor` не меняют файлы проекта/настройки пользователя.
- Прямой запуск Codex, повторные запуски bootstrap и откат не ломают существующие плагины/креденшалы.
- Версии, модели и репозитории benchmark известны; показатели воспроизводятся в контролируемых прогонах.
- Уменьшение токенов не достигается за счёт регрессии качества, сломанных тестов или недоказанных ответов.

## 8. Известные точки ревизии исходников

- `scripts/codex-smart` — навязывание lean, unused classifier, side-effect `.git/info/exclude`, аргументы запуска.
- `scripts/classify_repo.py` — полезность/стоимость классификации и учёт незакоммиченных файлов.
- `scripts/code-graph-smart` — dynamic `npx` package/version, контроль индекса, bounded output.
- `profiles/*.config.toml` — available tools, `enabled_tools`, reasoning modes.
- `bootstrap.sh`, `scripts/patch_config.py` — конфигурация, миграция, idempotency, backups.
- `skills/tool-router/SKILL.md`, `skills/verify-change/SKILL.md`, глобальный/проектный `AGENTS.md` — единая политика.
- `bench/*` — расширение задач и quality gates с retrieval-only на полную разработку.

## 9. Ограничения достоверности

Описание исходного кода относится к **архиву `v1.4.1`**, а не гарантированно к версии, установленной на ThinkPad 6 октября 2026 года. Бенчмарк измерял **retrieval / execution-path analysis**, а не end-to-end development. Новые стратегии — проектные гипотезы до независимого сравнения.
