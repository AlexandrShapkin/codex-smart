# P3: Implement release and migration workflow

This reference extends the original release/migration scope; GitHub #16 owns live
acceptance and retains its history. Planned owner: 0.7 Distribution.

## Context

Thin deterministic workflow optimizer; minimize total lifecycle cost subject to
required quality and verification. Existing Linux x86_64 artifact/checksum workflow
is readiness scaffolding, not published or authenticated distribution.

## Problem and scope

Own release metadata, prebuilt versioned artifacts, checksums, reviewed authenticity,
compatibility and supported matrix; tag/changelog/GitHub Release boundaries and
migration policy. Initial distribution remains Linux x86_64 unless evidence expands
it. Coordinate installer/uninstaller #50, updater/check/rollback #51 and migration/
interrupted-update rehearsal #52 through [distribution](../distribution.md).

## Non-goals

No publication without authorization, crates.io publication, unsupported platform
promise, silent installation/PATH/auth/plugin changes, credential copying or
unrelated dependencies. No installer/updater implementation in this roadmap PR.

## Acceptance criteria

Reviewed authenticity/trust-root and release metadata contract; artifact/checksum
validation and reproducibility limits documented. Explicit version/channel and
offline/local-artifact policy; compatibility preflight. Safe migration dry-run,
transactional backup/rollback and downgrade/interruption recovery with ownership
boundaries. Actual publication only authorized separately. No half-written binary/
config state; Codex credentials remain untouched.

## Validation

Release dry-run artifact/authenticity/checksum controls; clean install/update/
rollback/uninstall and failure-recovery rehearsals through #50–#52; exact-head CI,
independent review and Security. No tags/releases or package version bump here.

## Dependencies

- #6 safe configuration and migration model; #8 CI quality gates (retained history).
- #15 separate optional aggregate telemetry; never a private-logging requirement.
- #49 accepted recurring-workflow automation before distribution implementation.
- #50, #51 and #52 provide distribution completion evidence; each depends on this
  issue's reviewed release contract, avoiding a circular implementation prerequisite.

## Known risks

Trust-root compromise, stale metadata, release reproducibility limits, transaction
races and incompatible downgrade. Unknown compatibility/authenticity fails closed.
